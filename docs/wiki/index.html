Proxy ELK

Proxy d’authentification et d’autorisation devant un Elasticsearch self-hosted, avec un assistant IA prévu dans Kibana via un plugin minimal. Open source — licence Apache-2.0.

Périmètre actuel (jalon 1) — authentification (OIDC, LDAP/AD, JWT M2M, Kerberos), ACL en lecture seule, audit JSON, quotas, relais Elasticsearch avec es-security-runas-user, image Docker et binaire systemd. Kibana Cloud est hors scope.

Pourquoi

Certaines fonctions de sécurité d’Elasticsearch (LDAP / Active Directory, SSO, audit) sont réservées aux offres payantes. Ce projet les apporte devant Elasticsearch, sans toucher au code Elastic ni à sa vérification de licence.

  • Un seul chemin vers Elasticsearch : le proxy.
  • Identité résolue hors d’Elastic (OIDC, LDAP, JWT, Kerberos).
  • Décision d’accès déclarative (ACL fail-closed, lecture seule).
  • Impersonation upstream via un compte de service + es-security-runas-user — le mot de passe de l’utilisateur n’atteint jamais Elasticsearch.

Principes

Deny by default
Toute route ou action non reconnue est refusée.
Droits de l’utilisateur
L’IA n’a jamais plus de droits que la personne connectée.
Lecture seule
Tout ce que l’IA génère reste en lecture seule. Les règles ACL ne peuvent accorder que read.
Transparence
La requête générée est toujours visible et rejouable.
Self-hosted
Kibana self-hosted uniquement. Elastic Cloud est hors scope.

Architecture

Le proxy est un binaire Go statique (cmd/proxy) qui écoute HTTP, authentifie l’appelant, décide via l’ACL, puis relaie vers Elasticsearch. Kibana ne parle jamais directement au cluster ES : dans la démo, ES n’a même pas de port exposé sur l’hôte.

Client / Kibana │ ▼ ┌──────────────── Proxy ELK (:8080) ────────────────┐ │ /health /metrics (sans auth) │ │ /auth/* login OIDC|LDAP|Kerberos|JWT │ │ /* relais ES → identité → ACL → run_as │ └───────────────────────┬───────────────────────────┘ │ Basic (proxy_service) │ + es-security-runas-user: <subject> ▼ Elasticsearch

Flux d’une requête ES

  1. Identité : cookie de session, ou Bearer JWT, ou Basic (re-vérifié LDAP si besoin).
  2. Passthrough : si l’utilisateur est dans passthrough_users (ex. kibana_system), relais tel quel, sans ACL.
  3. Classification : méthode + chemin → read | write | cluster_admin.
  4. Résolution d’index : aliases → noms concrets via /_resolve/index (API key dédiée).
  5. Décision ACL : allow rules uniquement ; sinon 403.
  6. Relais : Basic du compte de service + en-tête es-security-runas-user.

Authentification

Chaque mécanisme se configure par une section YAML. L’omettre le désactive. OIDC, LDAP et Kerberos partagent la même session cookie HMAC (pas de store serveur).

OIDC (authorization code)

  • GET /auth/login → redirection vers l’IdP.
  • GET /auth/callback → échange du code, cookie de session, redirect /auth/me.
  • Claim groupes configurable (groups_claim, défaut groups).

LDAP / Active Directory

  • POST /auth/ldap — login username/password.
  • LDAPS ou LDAP + StartTLS ; plaintext uniquement avec insecure_allow_plaintext (dev).
  • Failover via urls: (liste ordonnée, exclusif avec url).
  • Groupes imbriqués AD : nested_groups: true (LDAP_MATCHING_RULE_IN_CHAIN).
  • Lockout par couple (user, IP) : max_failures / failure_window / lockout_for.
  • Filtre AD typique : (sAMAccountName=%s).

JWT machine-à-machine

  • Le proxy vérifie un Bearer JWT déjà émis par un IdP externe ; il n’en émet jamais.
  • Pas de cookie de session pour ces appelants.
  • Config : issuer, audience, jwks_url.

Kerberos / SPNEGO

  • Avec kerberos: + kibana:, GET /auth/kibana devient un challenge Negotiate (plus de formulaire).
  • Le proxy n’appelle jamais le KDC : seul le keytab monté suffit (pas de krb5.conf dans le conteneur).
  • Les groupes viennent toujours de LDAP (lookup).

Pont SSO Kibana

GET/POST /auth/kibana (nécessite ldap: et kibana:) authentifie l’utilisateur puis ouvre la session Kibana pour lui — l’écran de login Kibana n’apparaît pas. url = adresse appelée par le proxy ; public_url = redirection navigateur.

Session

Cookie HMAC signé, secret ≥ 32 octets (session.secret), TTL configurable (défaut 8 h). Flag Secure si oidc.redirect_url est en HTTPS.

ACL

Politique déclarative, allow rules uniquement, fail-closed. Le proxy refuse de démarrer sans au moins une règle. Une rule ne peut accorder que actions: [read] — write ou cluster_admin dans le YAML fait échouer le chargement.

Correspondance

  • Sujet dans users, ou intersection non vide avec groups.
  • Indices : motifs glob (path.Match) sur les noms concrets (aliases résolus d’abord).
  • Indices système (.kibana*, .security*, …) refusés par défaut sauf override system_indices.
  • known_groups (optionnel) : un groupe inconnu dans une rule fait échouer le load.

Classification des requêtes

ActionQuand
cluster_admin Préfixes /_cluster, /_security, /_nodes, /_license, /_snapshot, /_slm, /_tasks, /_cat
read GET/HEAD ; ou POST se terminant par /_search, /_msearch, /_count, /_field_caps, /_validate/query, /_async_search
write Tout le reste
Une requête classée write ou cluster_admin est toujours refusée par Decide, même si l’index est couvert par une rule.

Conditions optionnelles

Toutes les conditions présentes sur une rule doivent matcher :

  • source_ips — IP ou CIDR sur RemoteAddr uniquement (jamais X-Forwarded-For)
  • methods — méthodes HTTP
  • time — fenêtre UTC from/to (HH:MM) et jours optionnels

Exemple

acl:
  rules:
    - name: equipe-a-read
      groups: [equipe-a-viewer, equipe-a-editor]
      indices: [equipe-a-*, shared-ref]
      actions: [read]
    - name: alice-extra
      users: [alice]
      indices: [alice-scratch]
      actions: [read]
      # source_ips: ["10.0.0.0/8"]
      # methods: [GET, POST]
      # time: { from: "08:00", to: "18:00", days: [Mon, Tue, Wed, Thu, Fri] }

Simulation hors ligne

proxy -config /etc/proxy/proxy.yaml -simulate \
  -subject alice -groups equipe-a-viewer \
  -index equipe-a-sample -action read
# → allow equipe-a-read

Rechargement à chaud de l’ACL : SIGHUP (revalide toute la config ; en cas d’erreur, l’ancienne politique est conservée).

Relais Elasticsearch

  • run_as_user / run_as_password : compte de service pour l’auth upstream.
  • Après décision ACL positive : en-tête es-security-runas-user: <subject>.
  • api_key : uniquement pour le resolver (/_resolve/index), jamais sur la requête relayée.
  • shadow_password : secret native-realm substitué dans POST /_security/profile/_activate après re-vérification du mot de passe LDAP — jamais saisi par l’utilisateur, jamais envoyé à LDAP.
  • passthrough_users (défaut kibana_system) : relais inchangé avec les credentials Basic du client, hors ACL.

Quotas

Section limits optionnelle. Appliqués uniquement sur le handler catch-all (pas sur /health, /metrics, /auth/*).

  • max_duration, max_result_bytes, requests_per_minute
  • default pour les appelants sans rôle ; sinon aucun plafond
  • roles : groupes disjoints entre entrées ; si plusieurs matchent → minimum de chaque plafond

Configuration

Fichier YAML unique (défaut ./configs/proxy.yaml, flag -config). Les secrets sont des références, jamais des littéraux :

  • ${env:NAME} — variable d’environnement
  • ${file:/path} — contenu d’un fichier (secret monté)
Toujours citer les références : YAML traite un {...} non quoté comme un flow mapping.

Déploiement

Image Docker

Image produit seule (pas de compose de démo embarqué). Config 100 % fichier : monter le YAML en lecture seule, passer les secrets en variables d’environnement. Utilisateur non-root (uid 65532). 

docker build -t proxy-elk .
docker run --rm -p 8080:8080 \
  -e SESSION_SECRET=... -e ES_API_KEY=... \
  -e ES_RUN_AS_PASSWORD=... -e ES_SHADOW_PASSWORD=... \
  -v "$PWD/configs/my-proxy.yaml:/etc/proxy/proxy.yaml:ro" \
  proxy-elk
curl -sf localhost:8080/health
curl -sf localhost:8080/metrics | head

Binaire + systemd

Releases : archives proxy-elk_<version>_linux_{amd64,arm64}.tar.gz + SHA256SUMS (binaire, unit, YAML d’exemple, install.sh). 

# En root, depuis le répertoire décompressé de l’archive :
./install.sh
# → crée l’utilisateur système proxy, /etc/proxy, /etc/proxy/secrets
# Éditer /etc/proxy/proxy.yaml, créer les secrets (root:proxy 0640), puis :
systemctl enable --now proxy-elk

Relances ultérieures de install.sh : remplacent le binaire + l’unit et redémarrent le service ; /etc/proxy est préservé.

Durcissement unit : NoNewPrivileges, ProtectSystem=strict, ProtectHome, PrivateTmp.

Build local des archives

VERSION=v1.2.3 make release
# → dist/proxy-elk_v1.2.3_linux_amd64.tar.gz
# → dist/proxy-elk_v1.2.3_linux_arm64.tar.gz
# → dist/SHA256SUMS

Sécurité

Ne pas ouvrir d’issue publique pour une faille de sécurité. Utiliser l’onglet Security GitHub (« Report a vulnerability ») ou l’email indiqué dans SECURITY.md (objet [SECURITY] …).

Exemples de failles dans le périmètre :

  • Contournement auth / ACL (aliases, wildcards, indices système)
  • Accès à Elasticsearch sans passer par le proxy
  • Injection (LDAP, ES|QL, prompt) permettant lecture/écriture non autorisée
  • Fuite de secrets dans logs ou audit
  • Usurpation via tokens (JWT, en-têtes d’identité)

Accusé de réception sous 7 jours (engagement de bonne foi, pas un contrat de service). Divulgation coordonnée.
