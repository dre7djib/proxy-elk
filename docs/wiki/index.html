Proxy ELK

Authentication and authorization proxy in front of a self-hosted Elasticsearch, with an AI assistant in Kibana through a minimal plugin. Open source — Apache-2.0 license.

Current scope — milestone 1 is done: authentication (OIDC, LDAP/AD, M2M JWT, Kerberos), read-only ACL, JSON audit, quotas, Elasticsearch relay with es-security-runas-user, Docker image and systemd binary. Milestone 2 is in progress: /_proxy/ask assistant, ES|QL index guard, teams synced to Kibana, identity tokens. Elastic Cloud is out of scope.

Why

Some Elasticsearch security features (LDAP / Active Directory, SSO, audit) are reserved for paid tiers. This project brings them in front of Elasticsearch, without touching Elastic's code or its license check.

  • One single path to Elasticsearch: the proxy.
  • Identity resolved outside Elastic (OIDC, LDAP, JWT, Kerberos).
  • Declarative access decision (fail-closed, read-only ACL).
  • Upstream impersonation through a service account + es-security-runas-user — the user's password never reaches Elasticsearch.

Principles

Deny by default
Any unrecognized route or action is denied.
User's rights
The AI never has more rights than the logged-in person.
Read-only
Everything the AI generates stays read-only. ACL rules can only grant read.
Transparency
The generated query is always visible and replayable.
Self-hosted
Self-hosted Kibana only. Elastic Cloud is out of scope.

Architecture

The proxy is a static Go binary (cmd/proxy) that listens on HTTP, authenticates the caller, decides through the ACL, then relays to Elasticsearch. Kibana never talks to the ES cluster directly: in the demo, ES does not even expose a port on the host. See the interactive overview or the layer-by-layer pages.

Client / Kibana │ ▼ ┌──────────────── Proxy ELK (:8080) ────────────────┐ │ /health /metrics (no auth) │ │ /auth/* login OIDC|LDAP|Kerberos|JWT │ │ /* ES relay → identity → ACL → run_as │ └───────────────────────┬───────────────────────────┘ │ Basic (proxy_service) │ + es-security-runas-user: <subject> ▼ Elasticsearch

Flow of an ES request

  1. Identity: session cookie, Bearer JWT, or Basic (re-checked against LDAP when needed).
  2. Passthrough: if the user is in passthrough_users (e.g. kibana_system), relayed as is, without ACL.
  3. Classification: method + path → read | write | cluster_admin.
  4. Index resolution: aliases → concrete names via /_resolve/index (dedicated API key).
  5. ACL decision: allow rules only; otherwise 403.
  6. Relay: service account Basic + es-security-runas-user header.

Authentication

Each mechanism is configured by a YAML section; omitting it disables it. OIDC, LDAP and Kerberos share the same HMAC session cookie (no server-side store). Diagram: Layer 2 · Authentication.

OIDC (authorization code)

  • GET /auth/login → redirect to the IdP.
  • GET /auth/callback → code exchange, session cookie, redirect to /auth/me.
  • Configurable groups claim (groups_claim, default groups).

LDAP / Active Directory

  • POST /auth/ldap — username/password login.
  • LDAPS or LDAP + StartTLS; plaintext only with insecure_allow_plaintext (dev).
  • Failover via urls: (ordered list, exclusive with url).
  • AD nested groups: nested_groups: true (LDAP_MATCHING_RULE_IN_CHAIN).
  • Lockout per (user, IP) pair: max_failures / failure_window / lockout_for.
  • Typical AD filter: (sAMAccountName=%s).

Machine-to-machine JWT

  • The proxy verifies a Bearer JWT already issued by an external IdP; it never issues one.
  • No session cookie for these callers.
  • Config: issuer, audience, jwks_url.

Kerberos / SPNEGO

  • With kerberos: + kibana:, GET /auth/kibana becomes a Negotiate challenge (no more form).
  • The proxy never calls the KDC: the mounted keytab is enough (no krb5.conf in the container).
  • Groups always come from LDAP (lookup).

Kibana SSO bridge

GET/POST /auth/kibana (requires ldap: and kibana:) authenticates the user then opens the Kibana session on their behalf — the Kibana login screen never shows. url = address the proxy calls; public_url = browser redirect.

Session

HMAC-signed cookie, secret ≥ 32 bytes (session.secret), configurable TTL (default 8 h). Secure flag when oidc.redirect_url uses HTTPS.

Identity tokens (milestone 2)

With identity_token:, an authenticated user can call POST /_proxy/identity-token to get a short RS256 JWT (TTL 5–15 min, two keys for rotation) for the engine. Public keys are served at GET /identity/jwks. Service accounts (passthrough) get no token.

ACL

Declarative policy, allow rules only, fail-closed. The proxy refuses to start without at least one rule. A rule can only grant actions: [read] — write or cluster_admin in the YAML makes loading fail. Diagram: Layer 3 · Authorization.

Matching

  • Subject in users, or non-empty intersection with groups.
  • Indices: glob patterns (path.Match) on concrete names (aliases resolved first).
  • System indices (.kibana*, .security*, …) denied by default unless overridden by system_indices.
  • known_groups (optional): an unknown group in a rule makes loading fail.
  • teams: adds one read rule per team (team:<name>) for the union of its groups.

Request classification

ActionWhen
cluster_admin Prefixes /_cluster, /_security, /_nodes, /_license, /_snapshot, /_slm, /_tasks, /_cat
read GET/HEAD; or POST ending with /_search, /_msearch, /_count, /_field_caps, /_validate/query, /_async_search
write Everything else
A request classified write or cluster_admin is always denied by Decide, even if the index is covered by a rule.

ES|QL queries

POST /_query bodies are parsed: every index the query reads (FROM, LOOKUP JOIN, and the source indices of ENRICH policies) must pass the ACL. A query that cannot be parsed with certainty, a remote cluster or an unknown policy is denied.

Optional conditions

Every condition set on a rule must match:

  • source_ips — IP or CIDR on RemoteAddr only (never X-Forwarded-For)
  • methods — HTTP methods
  • time — UTC window from/to (HH:MM) and optional days

Example

acl:
  rules:
    - name: equipe-a-read
      groups: [equipe-a-viewer, equipe-a-editor]
      indices: [equipe-a-*, shared-ref]
      actions: [read]
    - name: alice-extra
      users: [alice]
      indices: [alice-scratch]
      actions: [read]
      # source_ips: ["10.0.0.0/8"]
      # methods: [GET, POST]
      # time: { from: "08:00", to: "18:00", days: [Mon, Tue, Wed, Thu, Fri] }

Offline simulation

proxy -config /etc/proxy/proxy.yaml -simulate \
  -subject alice -groups equipe-a-viewer \
  -index equipe-a-sample -action read
# → allow equipe-a-read

Hot reload of the ACL: SIGHUP (revalidates the whole config; on error, the previous policy is kept).

Elasticsearch relay

Diagram: Layer 4 · Elasticsearch.

  • run_as_user / run_as_password: service account for upstream authentication.
  • After a positive ACL decision: header es-security-runas-user: <subject>.
  • api_key: only for the resolver (/_resolve/index, ENRICH policies), never on the relayed request.
  • shadow_password: native-realm secret substituted in POST /_security/profile/_activate after re-checking the LDAP password — never typed by the user, never sent to LDAP.
  • passthrough_users (default kibana_system): relayed unchanged with the client's Basic credentials, outside the ACL.

Ask assistant (milestone 2)

With model: (any chat-completions API), POST /_proxy/ask turns a question into one read-only ES|QL query. The model only sees the fields of indices the caller may read; the query goes through the ES|QL check and runs as the caller, with one correction if it fails. Sending {"esql": …} replays an edited query without the model. Diagram: Layer 5 · AI assistant.

Quotas

Optional limits section. Applied only on the catch-all handler (not on /health, /metrics, /auth/*).

  • max_duration, max_result_bytes, requests_per_minute
  • default for callers with no role; otherwise no limit
  • roles: groups disjoint between entries; if several match → minimum of each limit

Configuration

A single YAML file (default ./configs/proxy.yaml, -config flag). Secrets are references, never literals:

  • ${env:NAME} — environment variable
  • ${file:/path} — file content (mounted secret)
Always quote references: YAML treats an unquoted {...} as a flow mapping.

Deployment

Docker image

Product image only (no demo compose inside). 100% file-based config: mount the YAML read-only, pass secrets as environment variables. Non-root user (uid 65532). 

docker build -t proxy-elk .
docker run --rm -p 8080:8080 \
  -e SESSION_SECRET=... -e ES_API_KEY=... \
  -e ES_RUN_AS_PASSWORD=... -e ES_SHADOW_PASSWORD=... \
  -v "$PWD/configs/my-proxy.yaml:/etc/proxy/proxy.yaml:ro" \
  proxy-elk
curl -sf localhost:8080/health
curl -sf localhost:8080/metrics | head

Binary + systemd

Releases: proxy-elk_<version>_linux_{amd64,arm64}.tar.gz archives + SHA256SUMS (binary, unit, example YAML, install.sh). 

# As root, from the unpacked archive directory:
./install.sh
# → creates the proxy system user, /etc/proxy, /etc/proxy/secrets
# Edit /etc/proxy/proxy.yaml, create the secrets (root:proxy 0640), then:
systemctl enable --now proxy-elk

Later runs of install.sh replace the binary and the unit and restart the service; /etc/proxy is preserved.

Unit hardening: NoNewPrivileges, ProtectSystem=strict, ProtectHome, PrivateTmp.

Building the archives locally

VERSION=v1.2.3 make release
# → dist/proxy-elk_v1.2.3_linux_amd64.tar.gz
# → dist/proxy-elk_v1.2.3_linux_arm64.tar.gz
# → dist/SHA256SUMS

Security

Do not open a public issue for a security vulnerability. Use the GitHub Security tab (“Report a vulnerability”) or the email given in SECURITY.md (subject [SECURITY] …).

Examples of in-scope vulnerabilities:

  • Auth / ACL bypass (aliases, wildcards, system indices)
  • Access to Elasticsearch without going through the proxy
  • Injection (LDAP, ES|QL, prompt) allowing unauthorized reads/writes
  • Secrets leaking into logs or audit
  • Impersonation through tokens (JWT, identity headers)

Acknowledgement within 7 days (a good-faith commitment, not a service contract). Coordinated disclosure.
